# Mode B 語料現況測試報告（B0）

> 2026-09-13。對象是 [`BLADE_CLOSEUP_SPEC.md`](../BLADE_CLOSEUP_SPEC.md) 的 B0 階段：
> 分類表、資料集授權表、語料實際 cm/px。分類表在 [`BLADE_CLOSEUP_TAXONOMY.md`](../BLADE_CLOSEUP_TAXONOMY.md)，
> 這一份是**資料面的實測**。
>
> **Mode B 尚未實作**，所以這裡沒有任何 Mode B 的準確率。報告量的是三件現在就量得到的事：
> 語料拿不拿得到、拿到的能不能用、既有程式碰到這種輸入會怎樣。

## 0. 五個結論

1. **三份主力語料只有一份可商用。** DTU Nordtank 的 **v2 是 CC BY-NC 3.0**（規格 §7 連的正是 v2），
   **v1 才是 CC BY 4.0**；Blade30 **完全沒有授權聲明**；Scientific Data 那份（figshare）是 **CC BY 4.0**。
2. **開放網路影像當語料是行不通的。** 200 張 CC 授權的「wind turbine blade」影像裡，
   符合 §1.2 取像條件的 23 張（11.5%），表面真的解析得出來的 **8 張（4.0%）**，
   **有缺陷的 0 張**。54% 根本不是風機葉片（噴射引擎與直升機旋翼）。
3. **cm/px 量不到，因為 EXIF 被剝掉了。** 開放網路語料 **0/200** 有 EXIF；
   唯一可商用的 multiclass 語料 **3/1065** 有 EXIF、**1/1065** 有焦距，而且全部被統一裁成 1024×1024。
   規格 §9.4（沒有尺度不得報 IEA Level）因此適用於**幾乎全部現有語料**。
4. **§1.2 的取像規則不保證解析度。** 「弦向橫跨畫面 ≥ 1/3」在 1024 px 的畫面上是 0.73 cm/px，
   **比 Mode A 地面 5x 的 0.37 還差**。要宣稱 IEA Level 1 得讓葉片**溢出畫面**，不是填滿 1/3。
5. **既有 Mode A 管線碰到近身照不會胡說。** 179 張非 Mode A 照片全部被拍攝閘門拒收（放行 0 張），
   而且是因為對的理由（葉片數不對 / 葉尖半徑離散），不是因為程式爆掉。

| **Multiclass WTB Defect Dataset** | **CC BY 4.0** | ✓ | figshare `10.6084/m9.figshare.30210175.v1`，79 MB 直連 | 本報告 §5 用的就是這份 |

三件要注意的事：

- **同一個 DOI 的兩個版本授權不同，而且是往更嚴的方向改。** v1 → v2 從 CC BY 4.0 變成 CC BY-NC 3.0。
  只記「DTU 是 CC」會出事，要記版本號。
- **沒有授權聲明不等於可以用。** Blade30 的 README 只寫「請引用這篇論文」，那是學術禮節不是授權。
  預設是著作權保留所有權利。要用得先寫信問作者，並把回覆存檔。
- **NC 的語料不能混進訓練資料。** 一旦混進去，整個模型的權重都帶著 NC 的限制，
  出貨時沒辦法事後拆開。這不是「先做研究之後再說」能繞過去的。

## 3. 開放網路影像能不能當語料（200 張實測）

用 Openverse API（只收 CC0 / CC BY / CC BY-SA）抓 200 張，14 個查詢字，逐張人工看圖判定。

| 判定 | 張數 | 占比 | 是什麼 |
|---|---|---|---|
| `out_of_domain` | 108 | 54.0% | 根本不是風機葉片 |
| `distant_blade` | 48 | 24.0% | 有葉片但太遠，弦向遠小於 1/3 |
| `mode_a` | 21 | 10.5% | 整台風機入鏡 → 這是 Mode A 的輸入 |
| `intake_pass_low_res` | 15 | 7.5% | 符合 §1.2 字面，但表面解析不出任何特徵 |
| `intake_pass_readable` | 8 | 4.0% | 符合 §1.2 且表面紋理看得出來 |

再往下切：8 張可判讀的裡面，**只有 3 張拍到的是氣動表面**（其餘 5 張是根部法蘭與根部圓柱）。
**有缺陷的 0 張**——8 張全是運輸途中的新葉片。

### 3.1 為什麼 54% 是垃圾

關鍵字搜尋在這個題目上特別糟，因為「turbine blade」與「rotor blade」在別的領域是更常見的詞：

- `turbine blade` → **噴射引擎與蒸汽輪機葉片**（#032–#049 幾乎整段）
- `rotor blade` → **直升機旋翼**（#064–#093 整段）
- `wind turbine maintenance` / `repair` → **美軍災害救援照片**（#128–#143 整段）
- `blade transport` → **鐵道攝影**（#160–#198，拍的是火車不是葉片）

這不是查詢字寫得不好可以修掉的。試過的做法：長查詢字（"wind turbine blade repair"）在 Openverse
只有 **7 筆**結果，短查詢字（"wind turbine blade"）有 240 筆但相關性崩掉——AND 比對讓這兩者之間
沒有中間地帶。

### 3.2 對規格的意義

規格 §1.3 說「公開語料全部落在這個範圍，限縮之後它們從『領域不匹配的參考』變成可以直接用」。
這一節的數字支持那個判斷，但要加一句：**能用的是專門採集的公開語料（DTU、Blade30、figshare），
不是開放網路影像。** 開放網路上湊不出 Mode B 的訓練集，也湊不出測試集——
**一張有缺陷的合格照片都沒有**。

（有一個例外值得記：#194 是一台農用風車的鐵葉片被吹彎，那是真的損傷照片，但設備類別不對。
關鍵字搜尋會把它送上來，人看得出來，模型不會。）

## 4. 語料實際 cm/px（B0 出口條件之三）

規格 §2 把這一項標成「待量」，說「同學的第一個量化任務是從 EXIF/XMP 取出實際焦段與距離」。

**結果是量不到，而且原因是結構性的。**

| 語料 | 張數 | 有任何 EXIF | 有焦距 | 有被攝距離 |
|---|---|---|---|---|
| 開放網路（Openverse） | 200 | **0** | 0 | 0 |
| Multiclass WTB（figshare） | 1065 | **3** | **1** | 0 |

原因不同但結果一樣：圖床（Flickr／Openverse）在重新編碼時剝掉 EXIF；
研究語料在裁切成統一尺寸時剝掉 EXIF。**兩邊都不是疏忽，是正常流程。**

### 4.1 沒有 EXIF 時還有什麼路

1. **畫面內的已知尺寸物件。** figshare 語料裡至少有一張把鋼尺放進畫面（`craze` 類）。
   這是規格 §4 `scale.method = reference_object` 的實例，**應該寫進拍攝規程**：
   每個機位第一張放一個已知長度的標記。
2. **葉片本身的已知尺寸。** 型錄有葉長與弦長分布。若能定出展向位置，弦寬就是尺。
   這與 Mode A §13 的「人工定錨 + 型錄尺度」是同一件事，兩個模式可以共用。
3. **無人機的 XMP。** DJI 的飛控在 XMP 裡寫相對高度與雲台角度，比 EXIF 完整。
   本報告沒有驗證過（手上的語料都沒有 XMP）——**這是 B0 還沒做完的部分**。

### 4.2 §1.2 的取像規則不保證解析度

規格 §1.2 用「葉片弦向橫跨畫面 ≥ 1/3」當合格判準。把它換算成 cm/px：

> cm/px = 弦長(cm) ÷ (畫面寬 ÷ 3)

| 畫面寬 px | 弦 1.5 m（外段） | 弦 2.5 m（中段） | 弦 4.0 m（根部） |
|---|---|---|---|
| 1024 | 0.439 | **0.732** | 1.172 |
| 1920 | 0.234 | 0.391 | 0.625 |
| 4000 | 0.113 | 0.188 | 0.300 |
| **5280**（DTU） | **0.085** | 0.142 | 0.227 |
| 8000 | 0.056 | 0.094 | 0.150 |

**在 1024 px 的畫面上剛好合格的照片是 0.73 cm/px——比 Mode A 地面 5x 在 50 m 的 0.37 還差一倍。**

反過來算，要達到分類表的解析度門檻，畫面寬至少要：

| 目標 | 弦 1.5 m | 弦 2.5 m | 弦 4.0 m |
|---|---|---|---|
| IEA Level 1（≤ 0.07 cm/px） | 6,429 px | **10,714 px** | 17,143 px |
| IEA Level 2（≤ 0.17 cm/px） | 2,647 px | 4,412 px | 7,059 px |
| Level 3 以上（≤ 0.46 cm/px） | 978 px | 1,630 px | 2,609 px |

**結論：在「弦向剛好占 1/3」的取像下，中段弦長要 Level 1 需要一萬像素寬的畫面，現在沒有這種相機。**
Level 1 只在兩種情況下做得到：（a）拍外段（弦短），且畫面寬 ≥ 6,400 px；
（b）**讓葉片溢出畫面**——只拍前緣一段，弦向不是 1/3 而是 3 倍。

後者正是「任何片段葉片照片」的意思，也正是規格 §1.2 目前寫的「合格」條件涵蓋不到的情況
（§1.2 只說下限，沒說「超過」也算）。**建議見 §7。**

## 5. 唯一可商用語料的實測（Multiclass WTB，1065 張）

figshare `10.6084/m9.figshare.30210175.v1`，CC BY 4.0，79 MB。Pascal VOC 標註，**兩位獨立標註者**。

### 5.1 類別分布

| 類別 | 標註框 | 張數（一張可多類） | 對到分類表 |
|---|---|---|---|
| `surface_injure` | 412 | 264 | `surface/coating_peeling` |
| `hide_craze` | 342 | 249 | `surface/gelcoat_crack_network` |
| `craze` | 257 | 198 | 目視多為開放型裂損（見下） |
| `corrosion` | 257 | 172 | 混了 `healthy/contamination` 與 `surface/corrosion_metal_part` |
| `crack` | 224 | 177 | `structural/structural_fracture`（**不是近身裂縫**） |
| `thunderstrike` | 92 | 89 | `environmental/lightning_damage` |

六類全部 ≥ 89 張，都過規格 §6 第 3 條的 30 張門檻。**這是好消息**——
Zhang 等人在 2 張上報 1.00/1.00 的情況在這份語料上不會發生。

影像全部 **1024×1024**（1 張 788×788）。標註框中位邊長 **237 px**，下四分位 143 px，最小 24 px。
換句話說**缺陷在畫面上很大**（線性尺度約占畫面 23%），這批不是在測小缺陷的偵測極限。

### 5.2 兩個實質問題

**（1）`crack` 類整類不在 Mode B 的輸入範圍。** 隨機抽 32 張逐張判定 §1.2 取像：

| 類別 | 取像合格 / 抽樣 |
|---|---|
| `hide_craze` | 6/6 |
| `surface_injure` | 5/5 |
| `corrosion` | 6/7 |
| `thunderstrike` | 3/4 |
| `craze` | 2/6 |
| **`crack`** | **0/6** |

整體 20/32 = 62% 合格。但 `crack` 抽到的 6 張**全部是整機照**（輪轂與塔架入鏡），
內容是葉片斷損而不是近身裂縫。依 §1.2 全數拒收。

這是真的兩難，不是標註問題：**安全上最關鍵的那一類，在這份語料裡拍的方式正好是 Mode B 收不進來的。**
（樣本只有每類 4–7 張，依 §6 第 3 條不報比率，只報張數與定性觀察。）

**（2）一張健康照都沒有。** 1065 張每一張都至少有一個缺陷框。規格 §6 第 4 條要求
「測試集裡至少 1/3 是健康照，且其中要刻意包含接縫、LEP 邊緣、VG 板、標記貼紙、汙漬」，
並要求誤報分開報「在正常結構上」與「在乾淨表面上」。**這份語料一條都滿足不了**：
沒有健康照，也沒有任何正常結構的正面標註。

用它可以訓練與量 recall，**不能量誤報**。而 §5.4 的 YOLOv8n 基線失敗方式正是誤報
（11 張健康照誤報在製造接縫與結構標記上）。**健康照與正常結構標註要自己補，這是 B0 之後的第一件事。**

### 5.3 標註者間一致度：可量測的上限

兩份標註用 IoU ≥ 0.5 配對後自行計算（`calculate_kappa.py` 需要 sklearn，本環境沒有，因此重寫一次）：

| 量 | 值 |
|---|---|
| A 的標註框 | 1,584 |
| B 的標註框 | 1,543 |
| IoU ≥ 0.5 配對成功 | 1,543 |
| 定位一致率（配對 ÷ 聯集） | 97.4% |
| **配對成功者的類別一致率** | **94.0%** |
| Cohen's kappa（含 background） | **0.897** |

**全部 92 次類別分歧只落在兩對上**：

| 分歧 | 次數 |
|---|---|
| `surface_injure` ↔ `corrosion` | 52 |
| `hide_craze` ↔ `craze` | 40 |

兩件事：

1. **94% 是任何模型在這份語料上的可量測上限。** 報超過它的分數就是在報雜訊。
   評估報告要把這個數字印在逐類表旁邊。
2. **這兩對界線畫得不夠利，而且是兩個獨立的人給的證據。** 分類表 §1 已經把它們列成
   `confused_with` 並寫了分辨規則，但顯然還不夠。B1 之前應該考慮：要嘛把每一對合併成一類，
   要嘛找到真正可操作的分辨判準（例如 `corrosion` 必須看到金屬件本體，`craze` 必須量得到開口寬度）。

## 6. 跨模式回歸：Mode A 吃近身照會怎樣

這一節測的是**已出貨的程式**，不是 Mode B。問題很具體：使用者把一張葉片近身照丟進既有的葉片
檢測流程，會拿到「拒收並說明原因」，還是拿到一份看起來合理的錯誤報告？

把 200 張全部餵進 `segment_turbine` → `find_structure` → `assess_capture`：

| 判定 | 張數 | 閘門放行 |
|---|---|---|
| `out_of_domain` | 108 | 0 |
| `distant_blade` | 48 | 0 |
| `mode_a` | 21 | **2** |
| `intake_pass_low_res` | 15 | 0 |
| `intake_pass_readable` | 8 | 0 |

**非 Mode A 的 179 張，閘門放行 0 張。**

拒收原因的分布（一張可多個原因）：葉片數不對 170、葉尖半徑離散 34、前景太少 3。
**沒有一張是靠「結構定位丟例外」擋下來的**——`find_structure` 每次都回傳了一個結構，
是閘門的條件把它擋掉的。這正是閘門該有的行為：它擋的是「算出東西但算錯」，不是「程式爆掉」。

放行的 2 張（#029、#095）都是乾淨天空下的單台風機，也就是 Mode A 真正要的輸入。
21 張整機照只過 2 張不代表閘門太嚴——這 21 張是隨手拍的風景照，不是引導拍攝流程下的照片。

**這一節可以當回歸測試**：`scripts/closeup_corpus_report.py --images <目錄>` 會重跑並與
`data/closeup_triage.json` 存的值比對，不一致就非零離開。

## 7. 對規格的四個修改建議

1. **§1.2 加一條解析度下限，與取景占比並列。** 目前的「弦向 ≥ 1/3」在低像素畫面上
   可以是 0.73 cm/px。建議改成兩條同時要滿足：取景占比 **且** `cm/px ≤ 該類別的門檻`
   （門檻已在分類表裡）。尺度未知時只能宣稱到 Level 3 以上。
2. **§1.2 明寫「溢出畫面」也是合格的。** 目前只寫下限，字面上讀不出「只拍前緣一段」算不算。
   §4.2 的算術顯示那正是 Level 1 唯一做得到的取像方式，規格應該把它寫成**建議**而不是留白。
3. **§7 的 DTU 連結改指 v1，並在表上標出每一份的版本與可商用性。** v2 是 NC。
4. **§10 的 B0 出口條件加一項：健康照與正常結構標註。** 現有可商用語料一張健康照都沒有，
   而規格 §6 第 4 條的誤報分項統計依賴它。不補這個，B2 的三條基線量得出 recall 但量不出誤報，
   而誤報正是 §5.4 監督式基線的失敗方式。

另外**不建議**改的一件事：`crack` 類與 §1.2 衝突（§5.2）**不要用放寬 §1.2 來解決**。
那一類本來就是 Mode A 抓得到的（三片剪影互比），讓它留在 Mode A 比讓 Mode B 什麼都收要好。
規格 §1.3 第 3 點「一個模式只解一種取像條件」在這裡應該守住。
