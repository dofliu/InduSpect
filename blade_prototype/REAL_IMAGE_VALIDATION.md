# 真實影像驗證 — 分割與結構定位

**日期**：2026-09-06　**對象**：`blade_proto.segmentation`（分割 + 結構定位）與其下游的三片幾何互比
**語料**：75 張 CC 授權的真實風機照片（Openverse），影像不進版控，標註在 `data/real_image_labels.json`

---

## 0. 為什麼做這件事

到這一步為止，葉片模組的所有門檻數字都來自 `blade_proto/synth.py` 產生的合成影像
（見 `SENSITIVITY.md`）。夾具和被測程式出自同一組假設——天空是平滑漸層、地面是一條矮
橫帶、畫面裡只有一台風機——這是循環驗證：合成資料證明的是「程式符合我對世界的假設」，
不是「程式在真實照片上會動」。

真實照片有雲、樹林、電線、多台同框、逆光、前景建物。這些不需要缺陷樣本就能測：**健康
風機的照片就足以回答「分割與結構定位會不會壞、壞的時候看不看得出來」**。

---

## 1. 結論（先講）

1. **乾淨天空底下可用，有雲就整個垮掉。** 30 張「單台主風機、整個轉子在框內」的照片中，
   晴空無雲的 14 張輪轂定位命中 12 張（86%）；有雲的 13 張只命中 1 張（8%），其中 4 張
   連遮罩都是空的。這不是取景距離的問題——同樣是「轉子夠大」的近景，晴空 12/14、
   有雲 0/5。**天空模型是目前唯一真正的瓶頸。**
2. **最危險的不是算錯，是算錯的時候看起來一樣正常。** 改動前 75 張裡有 6 張「超出設計
   範圍」的多台同框照片安靜地回傳了一組三葉結構；設計範圍內另有 7 張輪轂正確、卻把地面
   或樹線當成其中一片，三片互比照樣吐得出數字——24 張跑得到互比的照片有 23 張被判
   「離群」。若這些直接進報告，就是一份看起來合格的錯誤報告，而現場沒有人看得出差別。
3. **已修的兩件事讓範圍內的命中從 10/30 拉到 14/30**（set A：9/19 → 13/19），
   詳見 §3。**已擋下的一件事**：新增拍攝品質閘門，75 張裡放行 2 張，兩張都真正可用，
   零誤放行、零誤攔截（§4）。
4. **決定：Phase 1 之前要先補分割**，而且要補的是天空模型對雲的處理，不是結構定位。
   在那之前，葉片模組不得對雲天下的照片輸出幾何判定。

## 2. 語料與標註

| 批次 | 張數 | 用途 | 查詢字 |
|---|---|---|---|
| A | 45 | 開發與門檻選擇 | wind turbine / wind farm / wind turbine blades … |
| B | 30 | holdout，事後才抓，只用來覆核 | aerogenerador / windkraftanlage / éolienne / single wind turbine … |

抓取用 `scripts/fetch_real_images.py`（只收 CC0 / CC BY / CC BY-SA，出處與授權寫進
`manifest.json`）。影像本身在 `.gitignore`，版控裡只有標註與出處，任何人跑一次抓取腳本
就能重現。

> `upload.wikimedia.org` 從本環境的 proxy 出口會被限流（HTTP 429），連 Openverse 的縮圖
> 代理也拿不到 Wikimedia 的原檔，因此語料實際來自 Flickr / StockSnap 等可直連的來源。

**人工標註**（`data/real_image_labels.json`，75 張全部）：

- `category`：`single`（單台主風機、整個轉子在框內 = 演算法的設計輸入，30 張）／
  `multi`（多台同框或全遠景，33 張）／`none`（畫面裡沒有水平軸風機轉子，12 張）
- `hub`：輪轂中心的正規化座標。**30 張 single 全部**以 5 倍放大 + 2% 格線重讀過一次，
  精度約 ±0.01；重讀是在看演算法輸出之前對全部影像一次做完，不是只挑不合的改
  （第一次用 10% 粗格線讀，有 8 張誤差超過 3%，會系統性低估演算法）
- `sky`：`clear` / `cloud` / `backlit`，看照片判定，兩批同一條規則
- `framing`：轉子直徑相對畫面長邊，`near` ≥ 1/3、`mid` 1/6–1/3、`far` < 1/6

**判定標準**：`single` 看輪轂誤差是否 ≤ 畫面對角線的 5%；`multi` / `none` 看的不是定位
正確，而是**有沒有明確失敗**——安靜回傳一組合理的三葉結構比丟例外危險得多。

## 3. 量到的失敗模式與已修的部分

跑法：`python scripts/validate_real_images.py --dir real_images`（同時輸出逐張疊圖）。

### F1　地面與塔架連成同一元件 → 輪轂落在地面上（已修）

`_clean_mask` 靠「橫跨畫面 70% 寬、高度不到一半」認地面帶。真實照片的地面不是這樣：
它與塔架相連成同一個連通元件，於是又寬又高，規則整條失效。後果有兩層——距離變換最厚
的地方變成地面，`_tower_axis_from_bottom` 把整條地面帶當成「塔架」（中位寬度 = 畫面寬），
輪轂初估直接歪掉；就算輪轂僥倖正確，地面殘塊也會被歸類成一片葉片。

**修法**：新增 `find_horizon()`——地面在真實照片上有另一個穩定特徵：**整列幾乎都是前景**。
由畫面底部往上走高填充率的列，容許中斷 6 列，即可定出地平線；`find_structure(horizon_y=…)`
只在地平線以上做定位。

`b78792bf` 誤差 0.389 → 0.015（並從 0 片變成 3 片）、`1573f056` 2 片 → 3 片。

### F2　塔架中段的零星 3 臂點讓走訪提早停住（已修）

修好 F1 之後 `631b5a3e` 反而變差（0.043 → 0.447）——因為塔軸終於找得到了，暴露出
`_initial_hub_tower_first` 的停止條件寫錯：它在「連續 3 步不合格」就停。六點鐘葉片貼著
塔架時，塔身中段會出現零星的 3 臂點又掉回 2 臂，走訪就停在塔身中央。

**修法**：停止條件改成「軸線離開遮罩超過 3 步」；另加一條合理性檢查——轉子在框內時輪轂
上下都還有結構，落在整體高度最下緣 25% 的候選一律放棄，改用 DT + 臂數法。

`44f9c591` 0.568 → 0.016、`839eaf2b` 0.411 → 0.012、`3d8dac16` 0.264 → 0.009。

### F3　天空模型撐不住雲層（**未修，最大的一項**）

兩個方向都會壞：

- **雲被當成前景**：`b1fc10ba` 太陽在輪轂正後方，光暈整片進遮罩（前景占 51%），輪轂落在
  光暈裡；`6ae1af37` 的樹線、`c9d215f9` 的麥田被當成第三片葉片。
- **什麼都進不了遮罩**：邊界取樣帶本身就是雲或地物，robust MAD 被撐大，5.5σ 之下沒有
  任何像素——`d526cb66`、`2c9237a4`、`580e2493`、`a4b7f3db`、`fd7d67d4`、`c37ef14c`、
  `1a08b0fd`、`d0ed2613` 八張直接丟「遮罩為空」。

依天空條件切開（30 張 single，改動後）：

| 天空 | 張數 | 輪轂命中 | 找齊三片 | 遮罩全空 |
|---|---|---|---|---|
| clear（無雲、無直射光） | 14 | **12** | 7 | 0 |
| cloud（有明顯雲塊/雲幕） | 13 | **1** | 1 | 4 |
| backlit（太陽或夕陽正對鏡頭） | 3 | 1 | 0 | 0 |

取景不是主因：`near` 的 21 張命中 13、`mid` 的 8 張命中 1，但把兩個維度交叉之後
——**clear×near 12/14，cloud×near 0/5**——分開的是天空，不是距離。

**試過而且放棄的修法**（有量測才寫在這裡）：只用天空列估 robust scale（先用逐列中位色的
最大跳變找天空底緣，再把 MAD 限定在該區以上）。結果 30 張 single 的輪轂命中從 14 掉到
**11**：尺度變小以後雲塊與地面紋理大量進入遮罩，救回 `71bd6a66` 一張，卻打壞
`06a2eac4`（0.008 → 0.407）、`839eaf2b`（0.012 → 0.286）、`3d8dac16`、`dbc90d73`。
**放棄，不進版控。** 真正要換的是模型形式（例如逐區塊天空模型或分割網路），不是調尺度。

### F4　前景物件比風機更「厚」（未修）

`27f344ce` 的穀倉、`126b2482` 的人群：距離變換的峰值落在前景物上。這是 DT 法的固有弱點，
現階段由閘門擋下（前者三片半徑離散 0.27、後者 0 片）。

### F5　葉片貼齊塔架時只找得到兩片（不是 bug）

`631b5a3e`、`1573f056`、`9a1f100f`、`b4c1317b`：六點鐘方位的葉片與塔架合併，結構上就只有
兩個分支。這是幾何本身的限制，規格要求的是操作者避開這個方位角；閘門會據實回報
「只定位到 2 片」並要求重拍，不會假裝三片一致。

### F6　運動模糊的葉片分不出來（未修）

`79d39652` 暮色長曝，輪轂定位正確（誤差 0.011）但葉片全糊，0 片。閘門拒收。

## 4. 拍攝品質閘門（新增 `blade_proto/quality.py`）

閘門不判斷葉片好壞，只判斷**這張照片能不能拿來判斷**。它跑在結構定位之後、三片互比之前。

**拒收條件**

| 條件 | 依據 |
|---|---|
| 結構定位丟例外 | 天空模型壞了 |
| 前景 < 0.15% | 白葉片對上亮雲天空，對比不足 |
| 葉片數 ≠ 3 | 葉片貼塔架、沒入雲層或運動模糊 |
| 三片葉尖半徑離散 (max−min)/median > 15% | 同一台風機三片等長；差這麼多代表有一片是地物、電線或別台風機 |
| 任一葉尖落在地平線以下 | 抓到的不是葉片 |

**只警告不拒收**：地平線以上前景占比 > 15%、找不到塔架、輪轂未經精修、結構定位備註。

**門檻怎麼來的（含一條被量測否決的規則）**：對 75 張做二維掃描。

| 地平線以上前景上限 | 半徑離散上限 | set A 放行 / 其中可用 | set B 放行 / 其中可用 |
|---|---|---|---|
| 0.15 | 0.15 | 1 / 1 | 0 / 0 |
| 0.15 | 不限 | 6 / 1 | 3 / 0 |
| 不限 | 0.15 | **2 / 2** | **0 / 0** |
| 不限 | 0.25 | 2 / 2 | 1 / 0 |
| 不限 | 不限 | 11 / 2 | 3 / 0 |

半徑離散這一條把工作全做完了：它零誤放行，而前景占比那一條額外擋掉的只有一張**正確**
案例（`309348db`，岩石地面讓地平線以上仍有 20% 前景），一張錯誤案例都沒多擋。因此把它
**降級成警告**——這是量測改掉設計，不是設計猜出門檻。

**最終表現（A + B 共 75 張）**：放行 2 張（`309348db`、`06a2eac4`），兩張都是輪轂正確、
三片齊全、半徑一致的案例；誤放行 0、誤攔截 0。

放行率 2/75 看起來很低，但那正是重點：**這 75 張是「網路上找得到的風機照片」，不是依
`BLADE_INSPECTION_SPEC.md` 拍攝規範拍出來的照片**。閘門的意義是把「安靜的錯答案」換成
「明確的重拍指示」，不是提高通過率。報告端配合修改：`capture_quality.ok = False` 時，
幾何層只印重拍指示，整段互比表格與離群判定都不出現。

## 6. 對後續的影響

1. **Phase 1（App 化）之前先補分割**，而且只補一件事：天空模型對雲層的處理。目前的
   「逐列多項式 + 全域 robust 尺度」在單一漸層天空成立，在有雲的天空不成立，兩個方向都會壞。
   可行方向：逐區塊天空模型、或直接換成分割網路（雲/天空/結構三類）。
2. **`SENSITIVITY.md` 的數字只在乾淨天空下成立**——那份靈敏度分析是在合成天空上做的，
   本次量到的是「進得了那條管線的照片才適用」。已在該文件加註。
3. **拍攝規範要寫死「乾淨天空」**：`BLADE_INSPECTION_SPEC.md` §3 的拍攝條件必須把
   「避開雲塊背景、避開逆光」從建議提升為前置條件，並在 App 端於拍攝當下就用閘門即時提示。
4. **三片半徑一致性是最便宜的正確性檢查**，值得直接做進 App 的拍攝引導：拍完立刻算，
   不一致就當場要求重拍，不必等到分析階段。

## 7. 重現方式

```bash
cd blade_prototype
pip install -r requirements.txt
python scripts/fetch_real_images.py   --out real_images   --limit 45   # 依 data/real_image_labels.json 的 id 對照
python scripts/validate_real_images.py --dir real_images --out real_images/_out
# 圖文報告（本文件的圖文版，含逐個失敗模式的疊圖）
python scripts/make_validation_report.py --corpus real_images --after real_images/_out \
  --out validation.html --pdf validation.pdf
```

要重現**改動前後對照**，得先把 `blade_proto/segmentation.py` 退回修 `find_horizon` 與塔軸走訪
之前的版本再跑一次 validate，然後把兩個輸出目錄分別餵給 `--before` / `--after`；
`make_validation_report.py` 的 docstring 有完整指令。

`real_images/` 已在 `.gitignore`；`_out/` 內含逐張疊圖（洋紅 = 遮罩、綠 = 演算法輪轂、
黃圈 = 人工標註輪轂、青 = 葉尖）與 `results.json`。Openverse 的搜尋結果會隨時間變動，
若某個 id 抓不到，以 `manifest.json` 記的 landing URL 為準。
